# T5.3 无头截图黑帧：调查结论（已在 CI 实测结案）

调查日期：2026-08-19
针对提交：`8ecacf8` → `a5f1efb`（9 个连续 fix）与
`visual-review/official-99f6f02/welcome-no-workspace-light.md` 的「系统渲染例外」结论。

---

## 结论：原判定被实测证伪，根因不是黑帧

原判定：

> 「该无头 WindowServer 对这些路径要么返回无错误的黑 SDR 帧，要么拒绝产生可用合成图」
> → 归类为「T0.3/T2.6 允许的系统渲染例外」

**这是错误归因。** 在 macos-26 runner 上实测（分支 `ci/diagnose-snapshot-capture`）：

| 实测项 | 结果 |
|---|---|
| `csrutil status` | disabled |
| GUI session / Dock / loginwindow | 均存在，Aqua session 正常 |
| `CGPreflightScreenCaptureAccess()` | `true` |
| 裸 `screencapture -x` | 正常，截到完整菜单栏 + Dock |
| SCScreenshotManager 抓窗口 | **成功，非黑率 0.9998** |
| 其中 sidebar 材质带 | **非黑率 0.9996** |
| 其中 inspector 材质带 | **非黑率 0.9997** |

**ScreenCaptureKit 在 hosted runner 上能够完整合成系统材质。**
既不存在 TCC 拒绝，也不存在「无头 WindowServer 无法合成材质」的平台限制。
`nonblack_ratio=0.106` 的低值只是因为 runner 桌面背景本身就是纯黑，
不能用它单独判定黑帧。

## 真正的根因：显示器分辨率导致布局降级

runner 显示器默认 **1024x768**，而快照请求 **1280x840**。
AppKit 会把超出显示器的窗口**静默缩小**，实测 `frame` 被钳成 `1024x674`。

`refreshForCurrentViewport()` 随后按被钳制的真实宽度解算布局，
于是 `OfficialColumnLayout.resolve` 走进第三分支：

| viewport | 分支 | sidebar | center | details |
|---|---|---|---|---|
| 1280（基线期望） | 优先布局命中 | 280 | 640 | **360** |
| 1024（runner 实际） | **details 被丢弃** | 280 | 744 | **0** |

即 **CI 渲染的是两栏 shell，基线却是三栏**，比对当然大面积不同。
截图本身一直是好的，错的是被截的那个布局。

## 为什么 9 次修复全部「成功」却没解决问题

`SnapshotExporter` 在合成失败时静默回落到 `cacheDisplay(in:to:)`。
按 Apple WWDC 2018 Session 218 的原话，该 API
「is not going to capture some of our more advanced rendering techniques
like materials and blurs」。
于是每次失败都被伪装成绿色的 CI + 一张无材质的错误图片。

## 已实施的修复

1. **`native-ui.yml`**：截图前用 `displayplacer` 将显示器切到 `1920x1080`
   （实测该显示器支持至 1920x1080，仅默认停在 1024x768）。
   切换后 `frame=1280x840` 精确无钳制。
2. **`SnapshotExporter`**：新增视口钳制检测，实际 content size 与请求不符即
   `throw viewportClamped`；**删除 `cacheDisplay` 静默回退**，合成不可用或黑帧
   一律 fail。CI 不再可能用错误图片报成功。
3. **`compare_visual_pair.py`**：新增 `--column-fixtures`，从官方列布局 fixture
   （而非硬编码）派生 sidebar / inspector 材质带并排除，输出
   `contentExactChangedRatio` 等内容层指标。
   合成验证：注入已知 1% 内容层差异时，全图 `exactChangedRatio=0.50497`
   （复现实测的 0.507 底噪），而 `contentExactChangedRatio=0.00995` —— 
   证明那 0.5 的底噪**全部来自材质柱**，内容层实际只差约 0.7%。

## 已修复：titlebar 安全区导致的垂直错位

原以为是 24px 整体平移，实测后发现**不是平移**。sidebar 各元素定位：

| 元素 | official | native | delta | 距底部 |
|---|---|---|---|---|
| logo | 28 | 68 | **+40** | 812 / 772 |
| New Session | 74 | 115 | **+41** | 766 / 725 |
| Workspaces | 133 | 170 | **+37** | 707 / 670 |
| Settings | 801 | 803 | **+2** | 39 / 37 |

**顶部锚定元素下移约 40px，底部锚定元素几乎不动。**
根因是 `.titled` 窗口按 titlebar 安全区内缩内容，
shell 的可用高度比基线**少了约 40px** —— 这是视口变矮，不是整体平移。

因此**直接裁剪是错的**：裁掉顶部 40px 虽然对齐了 logo，
却会把 Settings 拖到 763（错位 -38），且导出高度变成 800，
`compare_visual_pair.py` 会因尺寸不一致直接 SystemExit。

正确做法：**先把窗口按安全区 inset 放大，使安全区恰好等于目标视口，
再从截图裁掉该band。** 顶部与底部锚定内容同时对齐，导出尺寸仍是 1280x840。
裁剪按图像实际像素高度换算 point→pixel，backing scale 非 1.0 时同样正确。
