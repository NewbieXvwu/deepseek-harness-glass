# T5.3 无头截图黑帧：外部调研与可执行诊断方案

调研日期：2026-08-19
针对提交：`8ecacf8` → `a5f1efb`（9 个连续 fix）与 `visual-review/official-99f6f02/welcome-no-workspace-light.md` 中「系统渲染例外」的结论。

---

## 0. 结论摘要

TODO 与 review 记录当前的判定是：

> 「该无头 WindowServer 对这些路径要么返回无错误的黑 SDR 帧，要么拒绝产生可用合成图」
> → 归类为「T0.3/T2.6 允许的系统渲染例外」

**这个判定缺少支撑证据，且很可能是错误归因。** 现有 9 次尝试全部在
`SnapshotExporter.swift` 内部变换 API 调用方式（SCScreenshotManager rect →
current-process window → alpha-first 黑帧拒绝 → `screencapture -l`），
但**从未验证过环境侧的三个前置条件**。三者中任意一个不满足，都会产生
「无错误的黑帧」这一完全相同的症状。

在环境侧假设被逐一排除之前，不能认定为平台不可行。这与项目宪章第 6 条
「失败关闭……记录事实；不得猜测」的要求一致：当前记录的是推论，不是事实。

---

## 1. 三个未被检验的假设

### H1：TCC（屏幕录制授权）缺失 — 最高优先级

macOS 的截图 API 在未获 `kTCCServiceScreenCapture` 授权时，**不报错，直接返回
黑帧或仅桌面背景**。这与观察到的症状逐字吻合。

本仓库同时命中了四个已知的 TCC 失败因子：

| 因子 | 本仓库现状 | 证据 |
|---|---|---|
| 缺 `NSScreenCaptureUsageDescription` | `glass/Info.plist` 中无此键 | ScreenCaptureKit 纯 TCC 门控，无 entitlement 可绕过；缺 purpose string 时系统可直接终止应用 |
| ad-hoc 签名 | `assemble.sh:51` `codesign --force --deep -s -` | ad-hoc 签名每次构建 code directory hash 都变，TCC 按此 hash 追踪授权 → 每次构建都是「新应用」。Sequoia 起对无 Team ID 的 ad-hoc 身份直接拒绝授权 |
| 直接执行二进制而非 `open` | `verify-native-shell.sh` 直接调 `"$BINARY"` | TCC 会把请求归属到**父进程**（shell/runner）而非 app bundle；须经 LaunchServices（`open -a`）启动才归属到 bundle |
| CI 从未处理 TCC | `.github/workflows/native-ui.yml` 中无 `tccutil`/`sqlite3`/TCC 相关步骤 | 全文 grep 无命中 |

补充：macOS 26（Tahoe）起，**非 bundle 的纯可执行文件不再出现在
Screen Recording 授权 UI 列表中**，相关问题在社区有明确记录
（trycua/cua#870，症状为「只截到桌面，截不到窗口」，SCK 报 `-3801`）。

### H2：bootstrap namespace 不在 Aqua 会话内

`screencapture(1)` man page 的 SECURITY CONSIDERATIONS 明确写：

> To capture screen content while logged in via ssh, you must launch
> screencapture in the same mach bootstrap hierarchy as loginwindow:
> `sudo launchctl bsexec $(pid of loginwindow) screencapture [options]`

GitHub Actions 的步骤由 runner 服务派生。若该服务不在 Aqua 会话的 bootstrap
层级内，进程根本连不上 WindowServer —— 表现同样是黑帧/失败。这解释了为什么
`screencapture -l<windowID>` 这条**独立于 SCK 的回退路径也失败**：两条路径
共享同一个 WindowServer 连接前提。

自托管 macOS runner 的社区实践一致印证此点：必须用 LaunchAgent（而非
`svc.sh` 的后台 daemon）+ 自动登录，才能让 GUI 测试拿到非黑截图。

### H3：无附着显示器

Apple Silicon 的托管 runner 是 VM。但这一条**已有反证**：
actions/runner-images#9330 中，用户在 macos-14 runner 上直接跑
`screencapture debugscreen.png`，拿到了一张**真实桌面截图**（画面里能看到
麦克风授权对话框）。说明托管 runner 存在可合成的 WindowServer 与帧缓冲。

同时 actions/runner-images#8951 的症状是「截图里没有已打开的应用、Dock 和
状态栏，只有桌面背景」—— 这正是 **TCC 被拒绝的典型签名**（拿得到桌面，
拿不到窗口），而非「没有显示器」。

→ **H3 基本可排除，H1/H2 高度可疑。**

## 2. 关键可行性证据：TCC 在 GH runner 上可被注入

- actions/runner-images#8162 确认：**macOS 13 起的托管 runner 镜像 SIP 是关闭的**
  （`csrutil status: disabled`）。
- actions/runner-images#9529 给出了已被采纳的可用 workaround：直接用 `sudo sqlite3`
  向系统级与用户级 `TCC.db` 的 `access` 表 `INSERT OR IGNORE` 一条
  `kTCCServiceScreenCapture` 记录。该 issue 中此法实测生效（并已提 PR #9530）。
  注意 Sonoma 起 `access` 表多出 4 列（pid / pid_version / boot_uuid /
  last_reminded），插入语句需按版本适配；macOS 26 需先 `PRAGMA table_info(access)`
  探测列数。

也就是说：**「无法在无头 runner 上授予屏幕录制权限」这个隐含前提是不成立的。**

## 3. 建议的诊断步骤（一个 CI 步骤即可定性，约 10 行）

在生成快照之前插入，把环境事实**打印为证据**，而不是继续猜：

```yaml
- name: Diagnose capture environment (evidence only)
  run: |
    echo "--- SIP ---";            csrutil status || true
    echo "--- session ---";        launchctl managername || true
    echo "--- loginwindow pid ---";pgrep -x loginwindow || echo "NO loginwindow"
    echo "--- displays ---";       system_profiler SPDisplaysDataType | head -40
    echo "--- TCC rows ---"
    sudo sqlite3 "/Library/Application Support/com.apple.TCC/TCC.db" \
      "SELECT service,client,auth_value FROM access WHERE service='kTCCServiceScreenCapture';" || true
    echo "--- baseline screencapture (full screen) ---"
    /usr/sbin/screencapture -x /tmp/full.png || echo "screencapture FAILED rc=$?"
    python3 - <<'PY'
    from PIL import Image; import os
    p="/tmp/full.png"
    print("exists:",os.path.exists(p))
    if os.path.exists(p):
        im=Image.open(p).convert("RGB"); print("size",im.size,"extrema",im.getextrema())
    PY
    echo "--- same, inside loginwindow bootstrap ---"
    sudo launchctl bsexec "$(pgrep -x loginwindow)" /usr/sbin/screencapture -x /tmp/bs.png \
      || echo "bsexec screencapture FAILED rc=$?"
```

判读表：

| 观察 | 结论 |
|---|---|
| `/tmp/full.png` 非纯黑、能看到桌面 | WindowServer 可合成 → H3 排除，问题在 TCC 或归属 |
| `/tmp/full.png` 是桌面但无窗口 | 典型 TCC 拒绝 → 走 §4 路径 A |
| `/tmp/full.png` 纯黑，但 `/tmp/bs.png` 正常 | bootstrap namespace 问题 → 走 §4 路径 A2 |
| 两者皆纯黑且无显示器 | 才可认定平台限制，此时结论才有证据 |

**在这个步骤跑出结果之前，T5.3 的「系统渲染例外」结论应当降级为「未诊断」。**

## 4. 三条修复路径（按代价排序）

### 路径 A：修 TCC + 正确启动（最小改动，最可能奏效）

1. `Info.plist` 增加 `NSScreenCaptureUsageDescription`（缺失时系统会终止触发
   TCC 提示的应用）。
2. CI 中按 #9529 的方式向系统级与用户级 TCC.db 注入
   `kTCCServiceScreenCapture` 授权，client 用 bundle id
   `com.dsh.desktop.glass`（`csreq` 列留 NULL，SIP 已关可行）。
3. **改用 `open -a "$APP" --args ...` 或 `open -na` 启动**，让 TCC 归属到
   bundle 而非父 shell；快照参数改由 argv 或 plist 传递（`open` 不透传环境变量，
   需用 `--env` 或改造参数传递方式）。
4. 在导出器入口调 `CGPreflightScreenCaptureAccess()` 并打印结果，**授权为 false
   时直接 fail CI**，而不是静默回退到 AppKit 位图。这一条最重要：当前的静默回退
   正是掩盖了根因、让 9 次尝试都「成功」产出了工件的原因。

（可选）若 ad-hoc 签名仍导致授权在每次构建失效，可在 CI 内生成一张自签名证书
并保持稳定 subject，或改为按路径而非 code hash 授权。

### 路径 A2：若诊断指向 H2

用 `sudo launchctl bsexec "$(pgrep -x loginwindow)"` 或
`launchctl asuser "$(id -u)"` 包裹应用启动与截图，使其进入 Aqua bootstrap。

### 路径 B：改用 XCUITest 截图（绕开 TCC，工程上最干净）

`XCUIScreen.main.screenshot()` / `XCUIApplication().screenshot()` 经测试
harness 取图，**不走 kTCCServiceScreenCapture 授权路径**，是 CI 上取得
真实合成画面（含系统材质）的常规做法，产物以 XCTAttachment 落到 `.xcresult`，
可用 `xcrun xcresulttool export attachments` 导出为 PNG。

代价：需要新增一个 UI Test target（当前 `Package.swift` 五个 target 中没有），
且要从 SwiftPM 切到 xcodebuild 驱动这部分测试。但这同时也是 T12.5
「macOS 自动化 UI tests」的既定任务，**两件事可以合并做**。

### 路径 C：自托管 runner / macOS VM（最高保真，最高运维成本）

Tart/Cirrus 或 AWS EC2 Mac + 自动登录 + LaunchAgent 方式运行 runner，获得
真实 Aqua 会话。社区实践表明这能彻底解决 GUI 测试黑截图。仅在 A/B 都失败时考虑。

## 5. 一个独立的、更根本的问题：系统材质本就不该进像素 diff

即使截图修好了，当前的比对设计仍有缺陷，值得单独处理。

**Apple 官方明确说明**（WWDC 2018 Session 218《Advanced Dark Mode》）：

> if you're using the NSView `cacheDisplay(in:to:)` method to cache your image
> to a bitmap rep, just be aware that this method is **not going to capture
> some of our more advanced rendering techniques like materials and blurs**

所以 `SnapshotExporter.fallbackBitmap` 那条 `cacheDisplay` 路径**在任何机器上
（包括本地开发机）都不可能渲染出 sidebar/inspector 材质**——这不是无头环境
特有的问题。注释里写的「cacheDisplay cannot render WindowServer-owned
materials」是对的，且有官方背书，这一点 agent 判断准确。

但由此产生的后果被低估了：**黑色区域没有被排除出比对，直接污染了度量。**
三次 review 记录的数字是：

| 指标 | T5.3 | T5.4 | T5.5 |
|---|---|---|---|
| materially changed ratio | 0.03564 | 0.03575 | 0.03570 |
| mean abs channel diff | 5.989 | 6.159 | 6.065 |
| **exact changed ratio** | **0.50733** | 0.50733 | 0.50733 |

`exact changed ratio ≈ 0.507`：**整幅图超过一半的像素与官方不同**，且三次几乎
逐位不变——这是 sidebar + inspector 两块恒定黑区贡献的常量。这个指标已经失去
回归信号能力：任何真实的内容层回归都会被这个 0.507 的底噪淹没，而
`welcome-no-workspace-light` 场景也因此**永远无法从 `report-only` 收敛到
`enforce`**，T5.6 之后的每个 UI 场景都会继承这个问题。

这其实与项目自己的 T0.3 策略相矛盾。`VISUAL_REPLICATION_TEST_PLAN.md` 已经
规定：系统材质只验证 API 使用、层级、可读性与辅助功能响应，**不作逐像素
失败判定**。既然如此，正确做法是：

1. 在 `visual-validation-policy.json` 中为每个场景声明**材质区域的排除矩形**
   （sidebar 与 inspector 的列宽已由 `OfficialColumnLayout.resolve` 精确给出，
   矩形可从布局求解器直接派生，无需硬编码）；
2. `compare_visual_pair.py` 对排除区外的内容层做严格比对，排除区仅做
   「存在性 + 几何位置 + 边界对齐」断言；
3. 材质本身的正确性继续由已有的 `check-native-structural-material.py`
   （强制 `NSSplitViewItem(sidebar/inspector:)`、禁止 `NSVisualEffectView`）
   和 `GlassPolicyTests` 的 Reduce Transparency / Increase Contrast 回归来保证。

这样即使截图路径最终仍拿不到系统材质，**内容层的像素验收依然可以 enforce**，
不必让整个视觉门禁停在 report-only。这一步的价值独立于 §4 是否成功，
建议无论如何都做。

## 6. 建议的执行顺序

1. **先跑 §3 诊断步骤**，把环境事实写进 review 记录（这一步本身就符合宪章
   「记录事实而非推论」的要求）。
2. 按诊断结果走 §4 路径 A / A2；把静默回退改成**授权失败即 fail**。
3. 无论 2 是否成功，都做 §5 的材质区域排除，让内容层比对可 enforce。
4. 若 A/A2 失败，把路径 B 与 T12.5 合并规划，而不是当作 T5.3 的补丁。
5. 更新 TODO 中 T5.3 的验收证据段落：当前表述「该无头 WindowServer 对这些路径
   要么返回无错误的黑 SDR 帧，要么拒绝产生可用合成图」应改为可证伪的事实陈述，
   并附诊断输出。
