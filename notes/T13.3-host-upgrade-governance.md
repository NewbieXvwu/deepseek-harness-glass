# T13.3：官方 Host 升级治理流程

## 目的与不变量

本流程约束任何 DeepSeek Harness Host、Web 前端或协议契约升级。升级不是单纯替换版本号；它必须形成一条可复核的证据链：**官方提交 → 规格输入 → 结构化生成物 → DTO/Host facade → 匿名化 fixture → reducer/transport 回归 → 原生视觉与无障碍 → 支持矩阵与发布工件**。

> 未完成本流程的升级不得被标注为“已支持”，也不得将未知 Host payload 作为已验证 authority 使用。

所有步骤使用独立、干净的官方工作树，禁止以开发者本地会话、私有路径、凭据或未经授权的对话内容作为 fixture 输入。所有产品 UI 文案继续只由锁定的 `OfficialUISpec` / `OfficialLocaleCatalog` 提供。

| 阶段 | 必须输入 | 必须输出 | 失败时的处理 |
|---|---|---|---|
| 1. 锁定官方来源 | 上游 tag/commit、版本与架构信息 | 精确 commit SHA、来源清单与支持候选 | 停止；不得猜测 API 或 UI 变化 |
| 2. 规格再生成 | 锁定官方工作树 | `official-ui-catalog.json`、`official-ui-spec-build.json`、主题/布局/交互场景结构化产物 | 修正生成器或审计差异，不手改生成结果掩盖变化 |
| 3. 协议审计 | 官方 RPC schema 与 endpoint contract | DTO manifest、transport contract fixture、facade 影响清单 | 新增/修改 typed DTO 与拒绝型负例，不添加字符串拼接 RPC |
| 4. 事件审计 | 官方 runtime test event builders 或经审计录制 | 匿名 raw-event replay fixture 与隐私审计 | 删除敏感输入；未知 event 必须安全忽略或显示官方 raw fallback |
| 5. 行为回归 | 新 DTO 与 replay fixture | reducer、SSE sequence fence、Host-authority、错误/重连回归 | 修复状态机；禁止以 UI 乐观状态掩盖 Host 分歧 |
| 6. 原生验收 | 完整 App、macOS GUI runner | Scene screenshot diff、AX tree、keyboard flow、性能/内存报告 | 保持 feature flag 隐藏或只读，不能宣称 UI parity |
| 7. 发布登记 | 全部证据与构建工件 | `SupportedHostBuilds.json`、release manifest、升级报告 | 不更新 default build，不发布可安装包 |

## 升级执行清单

### 1. 创建锁定来源

1. 记录候选 `dsh` package version、官方 Web 前端 package version、Node runtime、上游 tag 与完整 Git commit SHA。
2. 在独立官方工作树检出该 commit；不可复用含本地改动的参考目录。
3. 比对当前 `glass/Sources/Spec/OfficialUISpecBuild.swift`、`glass/Sources/Spec/OfficialUISpec/official-ui-spec-build.json` 和 `glass/Sources/Spec/SupportedHostBuilds.json` 的锁定来源。差异必须写入升级 PR 描述。
4. 在此阶段更新支持矩阵候选项，但**不得**切换默认 build。

### 2. 再生和审核官方规格

在锁定来源上运行项目的结构化规格检查，并将命令、官方 root 和 SHA 记录在升级报告：

```bash
python3 glass/ci/check-official-ui-spec-build.py --official-root /path/to/official
python3 glass/ci/check-official-theme-tokens.py --official-root /path/to/official
python3 glass/ci/check-official-column-layout-fixtures.py --official-root /path/to/official --node node
python3 glass/ci/check-official-interaction-scenes.py --official-root /path/to/official
```

审阅每项 upstream input、locale、icon、主题 token、几何与 visual scene 的结构化差异。不得以读取本项目 Swift 源码的关键词门禁代替运行时/结构化验证；若生成的 Swift public API 改变，必须由编译后 API 测试覆盖。

### 3. 更新协议与 facade

1. 将官方 RPC schema 的变化映射到 `DSHAPIClient.swift`、`DomainAPIs.swift`、`HarnessAPIs` 和明确的 typed facade。
2. 更新 `official-rpc-dto-manifest.json`、`official-transport-contract-manifest.json` 和相应 fixture，而非手写动态 method/payload 字典绕过 DTO。
3. 执行 transport contract、DTO fixture、Host build verifier 和 access policy 的正负例；未知/未验证 Host 仍必须拒绝写入、下载、插件和敏感 API。
4. 对每个新增 mutating API 添加至少一个拒绝/旧 revision/取消或重连负例。

### 4. 建立匿名 raw-event replay 证据

优先从锁定官方 runtime test builder 导出事件形状。若必须录制，录制前须确认授权，随后删除用户对话、凭据、私有路径、会话 ID 与 Host 配置。

`official-raw-event-replay-fixtures.json` 必须保留来源 commit、场景类别、匿名化策略和禁止值类。所有 fixture 在进入仓库前必须通过 catalog loader 与 payload 敏感标记负例。至少覆盖：happy path、错误、重连/重复 sequence、并发、长会话和 unknown node。

### 5. 验证 reducer、transport 和 Host authority

升级 PR 必须重放受影响 fixture，验证：

- 每个已支持 event/node 类型的 snapshot、turn/step boundary 与 stable key；
- unknown event 不崩溃、不伪造本地语义；
- SSE duplicate、乱序与跨 session sequence fence；
- prompt、模型、设置、workspace、approval/question 等 mutation 仅在 Host 接受或后续 Host snapshot 后成为 durable state；
- 旧 revision、迟到回包、取消和 Host restart 都不会复活过期 authority。

任何新增复杂 renderer 在官方 plugin/card 未加载时必须安全隐藏或呈现经过审计的原始 fallback，不能生成自创 summary 文案。

### 6. macOS 运行态验收

在 macOS GUI runner 上收集并附加：

1. 目标官方 scene 的 light/dark/system、窗口尺度和辅助功能条件下的 screenshot 及 diff；
2. AppKit/SwiftUI accessibility tree、注入违规 `WKWebView` 的负例，以及 keyboard/VoiceOver 流程；
3. 长会话、流式、长代码块和 sandbox 装卸的性能/内存结果；
4. 对更新表面进行 Host 断开、重连、拒绝、取消和错误恢复的运行态证据。

Linux 的结构化 gate、Swift 语法检查和可移植 pure-core tests 只能补充，不得替代该运行态验收。

### 7. 提交、支持矩阵与发布门

升级按以下小提交顺序提交，每一步同步 `TODO.md` 和本报告：

1. `chore(spec)`: 锁定官方来源与结构化 spec；
2. `feat(transport)`: DTO、facade、SupportedHostBuilds 候选；
3. `test(T12.1)`: 匿名 raw-event fixture 与隐私负例；
4. `test`: reducer、transport、Host-authority、错误与重连；
5. `test`: macOS visual/AX/keyboard/performance 证据；
6. `chore(release)`: 支持矩阵 default build、构建 manifest、签名/工件。

只有当所有必需 CI/运行态报告可追溯到该升级提交，并且 PR 描述同时包含 **official commit、spec revision、fixture revision、DTO/transport 影响、测试报告链接与 feature-flag 状态** 时，才可更新 `SupportedHostBuilds.json` 的默认 build 并进入发布流程。

## 结构化升级报告与 CI 门

每个已支持 Host baseline 必须同步更新 `glass/Sources/Spec/HostUpgradeReport.json`。该报告不替代 PR 的人工/macOS 运行态附件，而是把不可省略的官方 commit、default Host build、UI spec、protocol fixture、raw-event fixture、治理文档和测试工件路径登记为可机读事实。

`tools/check-host-upgrade-report.py --self-test` 已由 `documentation-integrity` workflow 在任何报告、支持矩阵、spec、locale 或 raw-event catalog 变更时执行。它只读取 JSON metadata 并验证登记 artifact 的存在：报告 commit 必须同时等于 default `SupportedHostBuilds`、UI spec、locale 与 raw-event catalog 的 commit；三个 revision 必须对应其结构化来源；required review stages 必须完整且唯一。其自测还以 commit mismatch 与缺失 artifact 负例证明 gate 可拒绝不完整升级，且从不读取或匹配本项目 Swift 源码。

> 该 gate 只验证当前 repository baseline 的可追溯性。Host 升级仍必须依次完成本文第 1–7 阶段，并在 PR 中附上 macOS screenshot/AX/keyboard/performance 的运行态工件；结构化 gate 不能被当作这些证据的替代品。

## 回滚

若任何 protocol replay、GUI evidence、sandbox isolation 或 release smoke test 失败，默认 build 保持上一个已验证条目。回滚仅恢复支持矩阵与 feature flags；不应删除失败升级的审计提交、fixture 或报告，以保留未来修复所需的可追溯证据。
