# T11.3：SwiftAdapterRegistry 合同与审计边界

**状态：** 已实现闭合 registry、可移植回归与 Core XCTest；本 TODO 仍未勾选，等待该提交的 macOS-26 构建与测试证据。

## 1. 身份与来源

锁定官方 settings 插件客户端为三张内置卡片分别绑定 `shell`、`agent-loop` 与 `web-search-deepseek` namespace，并在一次 activation 中构造固定 controller；未知 namespace 不应被客户端卡片猜测性渲染。[1] 项目 registry 因此为这些**已审阅的本地 settings adapter identities** 使用 `settings.shell`、`settings.agent-loop` 与 `settings.web-search-deepseek`，而不是把任意第三方 Cordis package name 或 slot contribution 自动转换为原生 adapter。

官方动态插件运行时以 `pluginId`、`packageId` 与 `pluginRunId` 追踪每一次浏览器半区激活，并通过 module loader 与 SlotRegistry 管理其 lifecycle。[2] `SwiftAdapterRegistry` 不试图替换或伪造这些运行时身份：它只记录 native fast-path 的 source-controlled metadata，在 T11.4 分流器中作为“可否优先选择原生”的明确信号。

| 枚举信息 | Registry 字段 | 目的 |
|---|---|---|
| 稳定的审阅 adapter 标识 | `adapterID` | 唯一、可审计、不可由插件运行时注册。 |
| 本地 fast-path plugin identity | `pluginID` | 仅精确匹配 source-controlled entry。 |
| Host compatibility | `minimumHostBuildID` | 当前必须与锁定 build 精确相等；不采用宽松版本范围。 |
| 回归证据 | `fixtureID` | 每一 adapter 关联明确 fixture 命名，供测试/诊断枚举。 |
| 原生实现类别 | `renderer` | 明示 `reviewedBuiltinCard` 或 `nativeSchemaForm`，不接受 plugin closure。 |

## 2. Admission 与失败语义

一个 adapter 仅在三个条件同时成立时 `active`：registry 中有精确 `pluginID`、当前 Host build 等于该 adapter 的锁定最低 build、且调用方已得到与该 plugin ID 相符的 T11.1 `.native` manifest route。任何未知 plugin、Host 不匹配或未验证 manifest 都返回 typed inactive reason；registry 不会自行回退、不会把第三方插件映射到内置视图，也不会执行动态代码。完整 inventory 无论 active 与否都会枚举所有 registry entries，便于 T11.4 诊断页显示运行轨与原因。

> Registry 的 inactive 状态不是失败的兼容判定。后续分流器应将未注册或 manifest 未验证的、可兼容插件交给 Ghost Plane；T11.3 仅负责说明原生快车道为什么没有生效。

## 3. 验证资产

`SwiftAdapterRegistryTests` 验证 shell adapter 的 active 条件、未知插件不能借用 adapter、Host mismatch、manifest 缺失和 inventory 全量枚举。`glass/ci/swift-adapter-registry-portable-check.swift` 直接使用生产 registry 与 manifest verifier 在 Linux Swift 6.2.4 通过，并已纳入 `portable-checks`。macOS-26 构建仍是含完整 Core target 的权威完成证据。
